# Workspace loss and recovery — 2026-05-06

On or around **2026-05-06 12:08**, the entire git working tree of this workspace
was deleted, including `.git/` itself. The loss was discovered on 2026-08-02 and
the workspace was reconstructed the same day. This document records what
happened, what came back, what did not, and how to redo the reconstruction if it
is ever needed again.

## What we know about the incident

The workspace was cleaned up deliberately once, on **2026-04-06**, to free disk
space; that cleanup is documented in `CLAUDE.md` and was intentional. The
**2026-05-06** event was separate and accidental.

Evidence:

- The `katago_workspace/` directory inode carried an mtime of `May 6 12:08` — the
  last time an entry was added to or removed from it. `runs/` and `.cache/` show
  the same timestamp.
- A directory snapshot embedded in an unrelated tool's config, written before
  2026-05-21, already shows the workspace in its post-deletion shape.
- No agent session log exists for that date in any of the assistant histories on
  this machine, so **who or what performed the deletion could not be
  determined**. Only its effect is known.

A later, unrelated rename (`_TO_DELETE_katago` → `katago_workspace`, 2026-08-02
17:44) moved nothing and deleted nothing; by then the directory was already in
its reduced state.

### The checkpoint-3000 consequence

`src/deployment/export_gguf_model_v4.sh` used to point at `checkpoint-3000`. It
now defaults to **`checkpoint-5000`**, the furthest-trained surviving adapter.
Re-running the export therefore produces a *different* model from the one on
HuggingFace. That is expected, and probably an improvement — but it means the
published GGUF is not locally reproducible, and the two should not be treated as
interchangeable when comparing results.

## Redoing the reconstruction from scratch

```bash
cd ~ && git clone https://github.com/BrightonLiu-zZ/KataGo-LLM-Team.git katago_workspace
cd katago_workspace

export HF_XET_CACHE=~/xet_cache_new     # avoid the root-owned xet cache
mkdir -p data

# Datasets and models
hf download brightonliuzZ/katago-grpo-datasets training_data_augmented_v3.jsonl \
    --repo-type=dataset --local-dir ./data
hf download brightonliuzZ/qwen3-8b-go-v4 qwen3-8b-go-v4-Q4_K_M.gguf \
    --repo-type=model --local-dir .
hf download brightonliuzZ/qwen3-8b-go-v4 --repo-type=model \
    --local-dir ./merged-qwen3-8b-go-v4 --exclude "qwen3-8b-go-v4-Q4_K_M.gguf"
hf download brightonliuzZ/grpo-go-checkpoints --repo-type=model --local-dir ./runs_hf

# Rebuild the derived datasets (needs ~4 GB RAM, ~5 minutes)
python3 src/data_acquiring/get_train_ready_data/shuffle_data.py
python3 src/data_acquiring/get_train_ready_data/prepare_v4_dataset.py
python3 src/data_acquiring/get_train_ready_data/reconstruct_quality_filtered_from_augmented.py

# KataGo engine
mkdir -p KataGo_engine
cp KataGo-1.16.4/cpp/KataGo_engine/katago KataGo_engine/katago && chmod +x KataGo_engine/katago
curl -L -o KataGo_engine/KataGo18b9x9.gz \
  https://media.katagotraining.org/uploaded/networks/models/kata1/kata1-b18c384nbt-s9996604416-d4316597426.bin.gz
```

Expected results: 270,000 shuffled records, 113,404 v4 records, 16,875
quality-filtered records.

## Preventing a repeat

- Anything large is safe only once it is on HuggingFace. See
  [ADR 0005](./adr/0005-huggingface-is-the-durable-store.md).
- `runs/` is gitignored, so surviving checkpoints exist in exactly one place.
  Push new checkpoints to `brightonliuzZ/grpo-go-checkpoints` as they are
  produced, not at cleanup time — `checkpoint-3000` was lost precisely because
  that step was deferred.
- Rollout logs are the only record of what the model actually generated during
  training. Archive them alongside the checkpoint they belong to.
